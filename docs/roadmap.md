# ロードマップ

実装の順番・範囲と確定した方針をまとめる。現在の仕様は各資料が正で、この資料は今後の変更を扱う。各項目は[開発ルール](../AGENTS.md)の順番（資料 → 失敗するテスト → 最小実装 → 不要コード・資料矛盾の確認）で、1項目を1つのPRとして進める。クラウドセッションでの進め方は[クラウドセッションでの開発](cloud-development.md)を参照する。

## 現在地

- MVPの受入条件M01〜M19は実装済み。
- 再帰スタック、問題の時間・メモリ制限の表示、誤差許容の比較、Windowsのメモリ上限、JITの調査、問題に応じた実行の打ち切り時間（5〜30秒）は実装済み（PR #29〜#34）。
- 実際に使い、次の課題が見つかった。
  - 開催中のコンテストの問題はログインしないと見られず、取得に失敗する。ログインなしでは4xxのエラーページが返り、ログイン画面へは転送されない。コンテストのトップページはログインなしでも開ける。終了後の問題はログインなしで取得できる。
  - 1問ずつURLを入れる「AtCoder の問題」は、コンテスト単位で取得できる問題集と役割が重なり、操作が煩雑。

## 確定した方針

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 問題の取得の入口 | 「コンテスト・問題集」に一本化し、「AtCoder の問題」（1問ずつの取得）と単問キャッシュを廃止する | AtCoderの問題はすべてコンテストに属し、コンテスト単位で取得できる |
| 開催中のコンテスト | ログインに対応して使えるようにする。提出機能は範囲外 | 練習だけでなく本番中にも使う |
| ファイルの読み書き | 外部ファイルの読み書き（ソースを開く・名前を付けて保存・新規、ケースJSONの読込・保存）を廃止する。解答とケースはユーザーデータ領域の問題ごとの作業領域にだけ保存する | 問題単位で使うアプリで、保存先を選ぶ操作とネイティブのファイルダイアログが不要になる |
| 問題を選んでいないとき | 問題を開くまでコードとケースを編集できない | 保存先が作業領域だけになるため、問題のない編集状態を持たない |
| 保存 | 解答とケースは作業領域へ自動保存する。未保存の破棄確認はなくす | 保存操作と確認ダイアログが不要になり、問題の切り替えも速くなる |
| 構成 | 画面・作業領域・問題の取得（ログインを含む）はWindowsに残し、Rubyの実行とRuby LSPはWSL内のエージェントに任せる | ログイン画面を利用者がWindowsで操作でき、日本語入力も今のまま。RubyはLinuxでAtCoderに近づける |
| WSL | 必須とする。Windows版Rubyは削除する | 2系統の実行環境を保守しない（KISS）。Windows固有のテストも減る |
| WSL側のRuby | CIでビルドしたLinux版Rubyをアプリに同梱し、初回起動時にWSL内へ配置する | 利用者がaptやsudoを使わずに済み、バージョンとハッシュを固定して同梱する方針を保てる |
| Rubyのバージョン | AtCoderと同じ3.4.5に合わせ、YJIT付きでビルドする | Linuxではバージョンを完全に合わせられ、AtCoderと同じ`--jit`も使える。ローカルで自分のコードを実行する用途のため、古いパッチによるセキュリティ上の影響は小さい |
| ログイン状態の保存 | WebView2のプロファイルの中だけに置き、アプリのファイルには書かない。パスワードは扱わない | ブラウザと同じ扱いにし、アプリが資格情報を直接保存しない |

WSL2はWindows 10（x64は1903・ビルド18362.1049以降）でも、Homeでも使える。CPUの仮想化機能を有効にする必要がある。

## 守ること

- 実際のAtCoderアカウントでのログインと、WSL2での通しの動作は、クラウドセッションやCIでは確かめられない。該当するPRは、利用者が手元で確認する手順（確認項目の一覧）を本文に書く。
- 開催中のコンテストの挙動は、開催中にしか確かめられない。各PRで、確認に使った開催中のコンテストと日時を記録する。
- 保存形式を変える場合は[保存形式を変えるときの方針](problem-library.md#保存形式を変えるときの方針)に従う。

## Phase A：取得の入口と作業領域の整理（Windows側）

### A1. CIの短縮

- 資料だけの変更（`docs/**`、`*.md`）ではCIを走らせない。テストが資料を読んでいないことを確認する。
- `concurrency`でワークフローとrefごとに古い実行を止める。
- Phase CでWindows版Rubyは削除するため、Rubyのダウンロードのキャッシュは追加しない。

### A2. 取得の入口を一本化

- 「AtCoder の問題」のボタン・ダイアログ、`problem_open`・`problem_refresh`、単問キャッシュ（`library/problems`）と関連コードを削除する。既存の単問キャッシュは読まず、不要なら手動で削除してよいと資料に書く。移行処理は作らない。
- 問題集のURL欄で問題URL（`/contests/<id>/tasks/<task>`）も受け付ける。そのコンテストを登録（登録済みならオフラインで再利用）し、取得後にその問題を開く。
- 解答とケースの作業領域（`workspaces/<contest>/<task>`）は変更しない。既存の解答・ケースが引き継がれることをテストで確認する。
- 問題一覧・問題ページが4xxを返したら、コンテストのトップページ（`/contests/<id>`）から開始・終了時刻を読み、開催中なら「開催中のコンテストの問題はログインが必要です」、開始前なら「コンテストの開始前です」と案内する。時刻を読めない場合はステータスコード付きの汎用エラーにする。実装前に開催中のコンテストで、ログインなしの実際のステータスコード・転送の有無・本文を確認して資料に記録する。通常のテストはローカルのHTTPサーバーで再現する。
- 「再取得」の代わりは既存の「取り直す」。ボタン名を「コンテスト・問題集」など、コンテストも入れられることが分かる名前にする。
- 単問の経路を使う画面テストと実サイトテストは、検証内容を保ったままコンテスト登録の経路へ移す。

### A3. 外部ファイルの読み書きを廃止し、作業領域への自動保存にする

- 「開く」「名前を付けて保存」「新規」と`Ctrl+O`・`Ctrl+Shift+S`、「ケース読込」「ケース保存」、関連するTauriコマンド（`document_open`・`samples_open`・`samples_save`など）、ネイティブのファイルダイアログを削除する。解答とケースの読み書きは作業領域（`workspaces/<contest>/<task>/solution.rb`・`cases.json`）だけにする。作業領域の保存形式は変えない。
- 問題を開くまでコードとケースは編集できず、実行もできない。起動時と問題を選んでいないときは、コンテスト・問題集から問題を開くよう案内する。初期サンプルのコードとケースはなくす。
- 解答とケースの編集は、少し待ってから作業領域へアトミックに自動保存する。問題の切り替え・ウィンドウを閉じる前は、保留中の保存を済ませてから進む。`Ctrl+S`はダイアログを出さずにすぐ保存する。保存状態（保存中・保存済み・失敗）を表示する。
- 保存に失敗した場合は編集内容をメモリに残してエラーを表示し、再試行できるようにする。失敗したまま問題を切り替える・閉じる場合だけ、アプリ内のダイアログで破棄の確認をする。保存が成功している状態では確認しない。
- 実行時の作業フォルダーは常に一時フォルダーにする（保存先のフォルダーで実行する仕様はなくす）。保存によって比較結果を解除する規則もなくす。
- ネイティブのダイアログを使わなくなったら`tauri-plugin-dialog`とWindowsのダイアログ自動操作（`native-dialog.ps1`）を削除する。
- 影響する受入条件（M02・M03・M07・M09・M14、R01・R06・R07など）と資料（mvp.md、architecture.md、multi-sample.md、problem-library.md、README.mdなど）を先に書き直す。手動保存のケースJSONに関する記述（保存形式の方針を含む）も整理する。ファイルダイアログを使う画面テストは、検証内容が残るものだけ作業領域の経路へ移す。

### A4. 問題文パネルから同じコンテストの問題へ切り替え

- 問題文パネルに同じコンテストの問題の一覧を出し、ダイアログを開かずに切り替えられるようにする。切り替え前に保留中の自動保存を済ませる。文書リビジョンによる保護は今の仕組みを使う。

## Phase B：開催中のコンテストへの対応（Windows側）

### B0. 調査（資料のみ）

- AtCoderの規約・コンテストのルールで、ログインした状態でツールが問題ページを取得することに制限がないかを確認し、出典付きで記録する。制限があれば以降の設計をそれに合わせる。
- ログイン画面の仕組み（CSRFトークン、自動操作対策の有無）を確認する。
- 開催中の問題を見るのに、ログインだけで足りるか、参加登録まで必要かを確認する。
- Tauri v2で、ログイン用ウィンドウ（WebView2）のCookieをRust側から読む方法（APIと必要なバージョン）を確認する。
- 結論をproblem-library.mdとarchitecture.mdに書き、「ログイン・認証情報は扱わない」を「パスワードは扱わない。ログインはAtCoderの画面で利用者が行う」に改める。

### B1. ログイン

- 「AtCoderにログイン」で別ウィンドウを開き、利用者がAtCoderの画面でログインする。このウィンドウは`atcoder.jp`以外へ移動させず、アプリの機能（IPC）を使えないようにする。
- 問題一覧・問題ページの取得時だけ、そのウィンドウのセッションを付けてGETする。POSTや提出は行わない。セッションはアプリのファイルに保存しない。
- ログイン状態の表示とログアウトを用意する。A2の「ログインが必要」の案内から、ログインへ移れるようにする。参加登録が必要な場合はその旨を案内する。

## Phase C：Rubyの実行とLSPをWSLのエージェントへ

### C0. 調査（資料と小さな試作）

- `wsl.exe`経由の標準入出力（1行ずつのJSON）の安定性、日本語、大量出力。
- WSLの起動時間（初回と2回目以降）と、エージェントの動作中はWSLが止まらないこと。
- Windows側から停止を依頼したとき、WSL内のプロセス群が確実に止まるか。
- コードは本文としてエージェントへ送り、実行時の作業フォルダーはWSL内の一時フォルダーにする（A3で保存先のフォルダーで実行する仕様はなくなるため、`C:\…`と`/mnt/c/…`の読み替えは不要）。日本語を含むコード・入出力の受け渡しを確認する。
- Linux版Ruby 3.4.5を、YJIT付き・配置場所に依存しない形（`--enable-load-relative`など）でCIでビルドできるか。対象のディストリビューションは`wsl --install`の既定（Ubuntu）。
- メモリ上限（`setrlimit`かcgroupか）と、ネイティブスタックの上限（`RLIMIT_STACK`）の扱い。
- GitHubのWindows環境でWSL1が使えるか。使えなければ、Windows側は偽のエージェントで確かめ、本物のエージェントはLinuxのCIで確かめる。

### C1. 資料の書き換え

- mvp.md（M10・M12・M19など）、architecture.md、atcoder-runtime.md、README.mdを「WSL2が必須、RubyはWSL内」の構成に書き直す。WSLの準備手順と、Windows 10 Homeでも使えること（仮想化を有効にする必要がある）を書く。

### C2. エージェント化

- 画面テスト用ホスト（`ui-test-host`）の通信方式をもとに、本番用のエージェント（Linux向けのバイナリ）を作る。Runner・LSP管理は既存のUnix向けのコードを使う。
- Windowsのアプリは起動時にエージェントを1つ立ち上げ、実行・停止・補完を中継する。ネットワークのポートは開かない。
- WSLがない・起動できない・ディストリビューションがない場合の案内を出す。
- LinuxのCIでは本物のエージェントで全テストを回す。

### C3. Linux版Rubyとgemの同梱

- C0の方式でRuby 3.4.5（YJIT付き）をビルドし、SHA-256を固定してアプリに同梱する。初回起動時にWSL内の決まった場所へ配置し、PATHには入れない。
- 既存の5つのgemに加え、ネイティブgem（rbtree、sorted_set、immutable-ruby、bit_utils、fast_trie、numo-narray、rumaleなど）を入れる。どこまで入れるかを理由付きでatcoder-runtime.mdに書く。
- Ruby LSPも同じRubyで動かす。
- 競技用gemをRuby LSPの解析対象に加え、ac-library-rbなどのAPIも補完候補に出す。先に、現状で競技用gemが解析対象に入っていないことをテストで確認する。競技側の実行からLSP用gemが見えないという既存の分離は維持する。

### C4. Windows版Rubyの関連を削除

- RubyInstallerの準備・更新、Windows Job Objectのメモリ上限、Windows向けの再帰・JITの測定などを削除する。
- WindowsのCIは、画面・ダイアログ・配布物・偽のエージェントでの確認に絞る。

### C5. 実行環境をAtCoderに近づける

- AtCoderと同じく`--jit`で実行する。メモリ上限・スタックの上限をLinuxの仕組みで設定する。
- 時間超過の注意表示の説明をJITありの前提に更新する。

## Phase D：残りの候補（使ってみて困った順）

- 問題集単位の明示的な全問取り直し（確認・中断・失敗分の再試行、解答・編集済みケースの保持）。
- 誤差許容を全ケースへ一度に設定する操作。
- AtCoderの言語アップデートへの追従手順（Rubyのバージョン、gem、LSPの依存の見直し）。
- 戻り値・複雑な制御フローの型推論の強化。

## 順番

A1 → A2 → A3 → A4 → B0 → B1 → C0 → C1 → C2 → C3 → C4 → C5 → D

- B0とC0は調査だけのため、A3・A4・B1と並行してよい。
- B1は開催中のコンテストで、利用者が手元で確認する。
