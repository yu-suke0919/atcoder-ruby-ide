# ロードマップ

実装の順番・範囲と確定した方針をまとめる。仕様は各資料が正とする。U1以降、画面と取得・保存の資料はPhase Uを終えた後の仕様を書き、実装はU2b〜U6で追いつく。どの仕様がどの項目で実装されるかはこの資料と[MVP](mvp.md)の受入条件で示す。各項目は[開発ルール](../AGENTS.md)の順番（資料 → 失敗するテスト → 最小実装 → 不要コード・資料矛盾の確認）で、1項目を1つのPRとして進める。クラウドセッションでの進め方は[クラウドセッションでの開発](cloud-development.md)を参照する。

## 現在地

- MVPの受入条件M01〜M19は実装済み。
- 再帰スタック、問題の時間・メモリ制限の表示、誤差許容の比較、Windowsのメモリ上限、JITの調査、問題に応じた実行の打ち切り時間（5〜30秒）は実装済み（PR #29〜#34）。
- CIの短縮（資料だけの変更では実行しない、同じrefの古い実行を止める）は実装済み。
- U0の調査は完了した。結論は[構成と検証方針](architecture.md#画面の作り直しの調査u0)と[問題ライブラリ](problem-library.md#atcoderからの読み取りの規約と頻度u0の調査)にある。ログインした状態の確認は利用者が手元で行い（[検証記録](verification.md#画面の作り直しの調査u0)）、開催中の問題はログインと参加登録を前提とすること、参加予定のコンテストの一覧ページはないこと、インストールしていないexeではトーストが出ないことを反映した。
- U1で、画面の仕様を[MVP](mvp.md)・[構成と検証方針](architecture.md)・[問題ライブラリ](problem-library.md)・[複数サンプル](multi-sample.md)・[エディタ仕様](code-editor.md)・READMEへ反映した。problem-presentation.mdは削除した。
- U2aで、外部ファイルの読み書きと破棄確認を削除し、問題を開くまで編集・実行できないようにして、解答とサンプルを作業領域へ自動保存するようにした。実行は常に一時フォルダーで行う。問題の入手方法と問題文の表示は変えていない。
- 実際に使い、次の課題が見つかった。
  - 開催中のコンテストの問題はログインしないと見られず、取得に失敗する。ログインなしでは4xxのエラーページが返り、ログイン画面へは転送されない。コンテストのトップページはログインなしでも開ける。終了後の問題はログインなしで取得できる。
  - 1問ずつURLを入れる「AtCoder の問題」は、コンテスト単位で取得できる問題集と役割が重なり、操作が煩雑。
- 開催中のコンテストでも使えるよう、画面を作り直す。新しい画面の仕様は[画面の仕様](ui.md)にまとめた。

## 確定した方針

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 画面 | [画面の仕様](ui.md)のとおり、左端のコンテスト・問題集、問題一覧、エディタとサンプル、AtCoderのページを表示するブラウザの4列にする。最小サイズは1280×720 | 開催中のコンテストで、問題を読む・解く・提出する流れを1つの画面で完結させる |
| 問題の取得の入口 | 参加登録したコンテストを自動で追加し、過去のコンテストと問題集は「＋」でURLを登録する。「AtCoder の問題」（1問ずつの取得）と単問キャッシュは廃止する | AtCoderの問題はすべてコンテストに属し、コンテスト単位で扱える |
| 問題文 | アプリでの解析・表示は廃止し、右端のブラウザでAtCoderのページを読む。サンプル・時間制限・入力形式だけをページから読み取って保存する | 表示はAtCoderに任せ、数式・画像の保存や検証などの仕組みをなくす（KISS） |
| 開催中のコンテスト | 右端のブラウザでログインして使う。参加登録と提出も利用者がブラウザで行い、アプリは提出結果を読み取るだけにする。アプリに提出機能は持たない | ログインは利用者がAtCoderの画面で行うのが確実で、アプリがID・パスワードを扱わずに済む |
| ログイン状態の保存 | ブラウザ（WebView2）のプロファイルの中だけに置き、アプリのファイルには書かない。パスワードは扱わない | ブラウザと同じ扱いにし、アプリが資格情報を直接保存しない |
| ファイルの読み書き | 外部ファイルの読み書き（ソースを開く・名前を付けて保存・新規、ケースJSONの読込・保存）を廃止する。解答とサンプルはユーザーデータ領域の問題ごとの作業領域にだけ保存する | 問題単位で使うアプリで、保存先を選ぶ操作とネイティブのファイルダイアログが不要になる |
| 問題を選んでいないとき | 問題を開くまでコードとサンプルを編集・実行できない | 保存先が作業領域だけになるため、問題のない編集状態を持たない |
| 保存 | 解答とサンプルは作業領域へ自動保存する。未保存の破棄確認はなくす | 保存操作と確認ダイアログが不要になり、問題の切り替えも速くなる |
| 1問のファイル | 1問に複数のファイルを持つ。既存の`solution.rb`は最初のファイルとして扱い、元のファイルを消さずに一度だけ変換する | 別解を並べて試せるようにする。変換は「移行は追加しない」の例外として利用者が決めた |
| 構成 | 画面・ブラウザ・作業領域・問題の取得はWindowsに残し、Rubyの実行とRuby LSPはWSL内のエージェントに任せる | ログインを含むブラウザ操作と日本語入力をWindowsで行い、RubyはLinuxでAtCoderに近づける |
| WSL | 必須とする。Windows版Rubyは削除する | 2系統の実行環境を保守しない（KISS）。Windows固有のテストも減る |
| WSL側のRuby | CIでビルドしたLinux版Rubyをアプリに同梱し、初回起動時にWSL内へ配置する | 利用者がaptやsudoを使わずに済み、バージョンとハッシュを固定して同梱する方針を保てる |
| Rubyのバージョン | AtCoderと同じ3.4.5に合わせ、YJIT付きでビルドする | Linuxではバージョンを完全に合わせられ、AtCoderと同じ`--jit`も使える。ローカルで自分のコードを実行する用途のため、古いパッチによるセキュリティ上の影響は小さい |

WSL2はWindows 10（x64は1903・ビルド18362.1049以降）でも、Homeでも使える。CPUの仮想化機能を有効にする必要がある。

## 守ること

- 実際のAtCoderアカウントでのログイン・参加登録・提出と、WSL2での通しの動作は、クラウドセッションやCIでは確かめられない。該当するPRは、利用者が手元で確認する手順（確認項目の一覧）を本文に書く。
- 開催中のコンテストの挙動は、開催中にしか確かめられない。各PRで、確認に使った開催中のコンテストと日時を記録する。
- 保存形式を変える場合は[保存形式を変えるときの方針](problem-library.md#保存形式を変えるときの方針)に従う。
- 右端のブラウザに表示するAtCoderのページから、アプリの機能（Rubyの実行、ファイルの読み書きなど）を呼べないようにする。

## Phase U：画面の作り直し（Windows側）

U2は差分が大きいため、問題の入手方法を変えないU2a（実装済み）と、入手方法を作り直すU2bの2つのPRに分けた。

### U2b. 4列の画面とブラウザ

- 4列の構成と最小サイズ1280×720、左端のアイコン（選択・「＋」での登録・右クリックでの非表示と復元）、問題一覧、右端のブラウザ（選択中のコンテスト・問題集の問題ごとに1つのページ、ログイン）を作る。分離は[画面の作り直しの調査](architecture.md#画面の作り直しの調査u0)に従う。問題ごとのページを8つ程度開いたときのメモリ使用量を測り、[検証記録](verification.md)に残す（利用者はメモリを多く使うことを許容している）。
- 「＋」での登録と問題一覧の取得、問題を開いたページからのサンプル・時間とメモリの制限の読み取り（`contests/`・`task.json`）を作る。問題を開いてサンプルを使えるようにするため、U4から前倒しする。
- 「AtCoder の問題」のボタン・ダイアログ、`problem_open`・`problem_refresh`、単問キャッシュ（`library/problems`）を削除する。
- 問題集のダイアログと一括取得・中断・再開・確認付きの取り直し、問題文の解析・表示（問題文パネル、`presentation.rs`の数式・画像の処理、問題集の本文の固定保存）を削除する。以前の`library/problems`・`library/collections`は読まない。

### U3. エディタとサンプル

- 1問に複数のファイルを持つ。初めて開いたときに空のファイルを2つ用意し、タブの「＋」で追加、右クリックで削除・名前の変更をする。実行するのは開いているタブ。
- 既存の`solution.rb`を最初のファイルへ一度だけ変換する。保存形式の変更なので、[保存形式を変えるときの方針](problem-library.md#保存形式を変えるときの方針)に従い、元のファイルを消さずに変換し、失敗時は元のまま残す。
- サンプルを問題ごとに全ファイルで共通にし、タブで切り替える。結果の枠に実際の出力、その下に折りたたんだ標準エラーを表示し、判定をタブの色で示す。
- 入力側に問題の時間制限、出力側に実際にかかった時間を表示する。許容誤差を問題ごとにする。実行・全件実行・停止のボタンをコード欄の下に浮かせて置く。

### U4. 入力形式の読み取りと入力コードの生成

- 問題を開いたページから入力形式を読み取り、`task.json`に保存する（サンプルと制限はU2bで読み取る）。
- 空のファイルを作るとき、入力形式から読み込みのコードを入れる。対応できる形をできる限り広げ（1行に複数の値、N行の入力、グリッド、文字列、クエリ形式など）、実際の問題の入力形式を固定データにしてテストする。形が判断できない場合は何も入れない。

### U5. 提出結果とクリップボード

- 右端のブラウザで行った提出の結果を読み取り、問題一覧の色（AC・AC以外・ジャッジ中）に反映する。結果はユーザーデータ領域に記憶し、アプリを閉じても残す。ジャッジ中の結果は、別の問題を開いていても更新する。
- ジャッジ中の結果は、提出一覧を表示しているWebViewの内容を読む（[読み取りの方法](architecture.md#ページからの読み取り)）。先に、数分以上隠したWebViewでもAtCoderのページが表示を更新し続けるかを確かめる。
- 比較が有効なサンプルがすべて一致した状態になったら、開いているファイルのコードをクリップボードへコピーする。設定（歯車）でオン・オフできるようにする。

### U6. 参加登録とコンテストの通知

- 右端のブラウザでの参加登録を検知してアイコンを追加する。参加予定のコンテストの一覧ページはないため、アプリの外で参加登録したコンテストは読まない。
- 参加登録で追加したコンテストは、終了から1日たったらアイコンを非表示にする。
- 参加登録で追加したコンテストの開始1分前に、Windowsのトーストで通知する（アプリの起動中だけ）。インストールしていないexeではトーストが出なかったため、先にインストール版で表示されるかを確かめ、出なければ通知の方法を決め直す。
- 参加登録で追加したコンテストの開始時（アプリの起動中だけ）に、問題一覧を取得して最初の問題を開く。他の問題は選んだときに取得する。取得の頻度は[問題ライブラリ](problem-library.md#取得の方針)に従う。

## Phase C：Rubyの実行とLSPをWSLのエージェントへ

### C0. 調査（資料と小さな試作）

- `wsl.exe`経由の標準入出力（1行ずつのJSON）の安定性、日本語、大量出力。
- WSLの起動時間（初回と2回目以降）と、エージェントの動作中はWSLが止まらないこと。
- Windows側から停止を依頼したとき、WSL内のプロセス群が確実に止まるか。
- コードは本文としてエージェントへ送り、実行時の作業フォルダーはWSL内の一時フォルダーにする（U2aで保存先のフォルダーで実行する仕様はなくなるため、`C:\…`と`/mnt/c/…`の読み替えは不要）。日本語を含むコード・入出力の受け渡しを確認する。
- Linux版Ruby 3.4.5を、YJIT付き・配置場所に依存しない形（`--enable-load-relative`など）でCIでビルドできるか。対象のディストリビューションは`wsl --install`の既定（Ubuntu）。
- メモリ上限（`setrlimit`かcgroupか）と、ネイティブスタックの上限（`RLIMIT_STACK`）の扱い。
- GitHubのWindows環境でWSL1が使えるか。使えなければ、Windows側は偽のエージェントで確かめ、本物のエージェントはLinuxのCIで確かめる。

### C1. 資料の書き換え

- mvp.md（M10・M12・M19など）、architecture.md、atcoder-runtime.md、README.mdを「WSL2が必須、RubyはWSL内」の構成に書き直す。WSLの準備手順と、Windows 10 Homeでも使えること（仮想化を有効にする必要がある）を書く。

### C2. エージェント化

- 画面テスト用ホスト（`ui-test-host`）の通信方式をもとに、本番用のエージェント（Linux向けのバイナリ）を作る。Runner・LSP管理は既存のUnix向けのコードを使う。
- Windowsのアプリは起動時にエージェントを1つ立ち上げ、実行・停止・補完を中継する。ネットワークのポートは開かない。
- WSLがない・起動できない・ディストリビューションがない場合の案内を出す。
- LinuxのCIでは本物のエージェントで全テストを回す。

### C3. Linux版Rubyとgemの同梱

- C0の方式でRuby 3.4.5（YJIT付き）をビルドし、SHA-256を固定してアプリに同梱する。初回起動時にWSL内の決まった場所へ配置し、PATHには入れない。
- 既存の5つのgemに加え、ネイティブgem（rbtree、sorted_set、immutable-ruby、bit_utils、fast_trie、numo-narray、rumaleなど）を入れる。どこまで入れるかを理由付きでatcoder-runtime.mdに書く。
- Ruby LSPも同じRubyで動かす。
- 競技用gemをRuby LSPの解析対象に加え、ac-library-rbなどのAPIも補完候補に出す。先に、現状で競技用gemが解析対象に入っていないことをテストで確認する。競技側の実行からLSP用gemが見えないという既存の分離は維持する。

### C4. Windows版Rubyの関連を削除

- RubyInstallerの準備・更新、Windows Job Objectのメモリ上限、Windows向けの再帰・JITの測定などを削除する。
- WindowsのCIは、画面・配布物・偽のエージェントでの確認に絞る。

### C5. 実行環境をAtCoderに近づける

- AtCoderと同じく`--jit`で実行する。メモリ上限・スタックの上限をLinuxの仕組みで設定する。
- 時間超過の注意表示の説明をJITありの前提に更新する。

## Phase D：残りの候補（使ってみて困った順）

- 誤差許容を全サンプルへ一度に設定する操作（問題ごとの設定で足りない場合）。
- AtCoderの言語アップデートへの追従手順（Rubyのバージョン、gem、LSPの依存の見直し）。
- 戻り値・複雑な制御フローの型推論の強化。

## 順番

U2b → U3 → U4 → U5 → U6 → C0 → C1 → C2 → C3 → C4 → C5 → D

- 開催中のコンテストで使えるようになるのはU2bの時点。U3以降は使いながら足していける。
- C0は調査だけのため、他の項目と並行してよい。
- Phase CはPhase Uと独立しているため、画面の作り直しを先に進め、後からRubyの実行環境を入れ替える。
