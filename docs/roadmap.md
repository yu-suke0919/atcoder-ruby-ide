実装の順番・範囲と確定した方針をまとめる。仕様は各資料が正とする。U1以降、画面と取得・保存の資料はPhase Uを終えた後の仕様を書き、実装はU5〜U6で追いつく。どの仕様がどの項目で実装されるかはこの資料と[MVP](mvp.md)の受入条件で示す。各項目は[開発ルール](../AGENTS.md)の順番（資料 → 失敗するテスト → 最小実装 → 不要コード・資料矛盾の確認）で、1項目を1つのPRとして進める。クラウドセッションでの進め方は[クラウドセッションでの開発](cloud-development.md)を参照する。

## 確定した方針

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 画面 | [画面の仕様](ui.md)のとおり、左端のコンテスト・問題集、問題一覧、エディタとサンプル、AtCoderのページを表示するブラウザの4列にする。最小サイズは1280×720 | 開催中のコンテストで、問題を読む・解く・提出する流れを1つの画面で完結させる |
| 問題の取得の入口 | 参加登録したコンテストを自動で追加し、過去のコンテストと問題集は「＋」でURLを登録する。「AtCoder の問題」（1問ずつの取得）と単問キャッシュは廃止する | AtCoderの問題はすべてコンテストに属し、コンテスト単位で扱える |
| 問題文 | アプリでの解析・表示は廃止し、右端のブラウザでAtCoderのページを読む。サンプル・時間制限・入力形式だけをページから読み取って保存する | 表示はAtCoderに任せ、数式・画像の保存や検証などの仕組みをなくす（KISS） |
| 開催中のコンテスト | 右端のブラウザでログインして使う。参加登録と提出も利用者がブラウザで行い、アプリは提出結果を読み取るだけにする。アプリに提出機能は持たない | ログインは利用者がAtCoderの画面で行うのが確実で、アプリがID・パスワードを扱わずに済む |
| ログイン状態の保存 | ブラウザ（WebView2）のプロファイルの中だけに置き、アプリのファイルには書かない。パスワードは扱わない | ブラウザと同じ扱いにし、アプリが資格情報を直接保存しない |
| ファイルの読み書き | 外部ファイルの読み書き（ソースを開く・名前を付けて保存・新規、ケースJSONの読込・保存）を廃止する。解答とサンプルはユーザーデータ領域の問題ごとの作業領域にだけ保存する | 問題単位で使うアプリで、保存先を選ぶ操作とネイティブのファイルダイアログが不要になる |
| 問題を選んでいないとき | 起動時はホームを開く。ホームでは問題とは別の作業領域でRubyを編集・実行できる。ホームまたは問題を開くまで編集・実行できない | 問題に関係なくRubyを試す場所を残しつつ、保存先を作業領域だけにして、保存先のない編集状態を持たない |
| 保存 | 解答とサンプルは作業領域へ自動保存する。未保存の破棄確認はなくす | 保存操作と確認ダイアログが不要になり、問題の切り替えも速くなる |
| 1問のファイル | 1問に複数のファイルを持つ。既存の`solution.rb`は最初のファイルとして扱い、元のファイルを消さずに一度だけ変換する | 別解を並べて試せるようにする。変換は「移行は追加しない」の例外として利用者が決めた |
| 構成 | 画面・ブラウザ・作業領域・問題の取得はWindowsに残し、Rubyの実行とRuby LSPはWSL内のエージェントに任せる | ログインを含むブラウザ操作と日本語入力をWindowsで行い、RubyはLinuxでAtCoderに近づける |
| WSL | 必須とする。Windows版Rubyは削除する | 2系統の実行環境を保守しない（KISS）。Windows固有のテストも減る |
| WSL側のRuby | CIでビルドしたLinux版Rubyを、アプリ専用の小さなディストリビューション（Ubuntu 22.04の最小構成）に入れ、初回起動時に`wsl --import`で登録する。C3cからは配布物に含めず、GitHubのReleasesに置いたものを初回起動時（と版が変わったとき）にダウンロードし、アプリに埋め込んだSHA-256で確かめてから登録する | 利用者はWSLの本体だけを入れればよく、Ubuntuの導入・初回設定・aptやsudoが要らない。利用者のディストリビューションと分かれ、環境とバージョンを固定できる。配布物はアプリ本体だけになり小さくなる（利用者の判断、2026-11-02）。Windows版Rubyをアプリ内に入れる選択肢は、2つの実行環境の保守とAtCoderとの差（JIT・C拡張のgem）のため持たない |
| Rubyのバージョン | AtCoderと同じ3.4.5に合わせ、YJIT付きでビルドする | Linuxではバージョンを完全に合わせられ、AtCoderと同じ`--jit`も使える。ローカルで自分のコードを実行する用途のため、古いパッチによるセキュリティ上の影響は小さい |

WSL2はWindows 10（x64は1903・ビルド18362.1049以降）でも、Homeでも使える。CPUの仮想化機能を有効にする必要がある。

## 守ること

- 実際のAtCoderアカウントでのログイン・参加登録・提出と、WSL2での通しの動作は、クラウドセッションやCIでは確かめられない。該当するPRは、利用者が手元で確認する手順（確認項目の一覧）を本文に書く。
- 開催中のコンテストの挙動は、開催中にしか確かめられない。各PRで、確認に使った開催中のコンテストと日時を記録する。
- 保存形式を変える場合は[保存形式を変えるときの方針](problem-library.md#保存形式を変えるときの方針)に従う。
- 右端のブラウザに表示するAtCoderのページから、アプリの機能（Rubyの実行、ファイルの読み書きなど）を呼べないようにする。

## Phase U：画面の作り直し（Windows側）

### U5a. 提出結果と問題一覧の色

- 右端のブラウザで自分の提出一覧（`/contests/<id>/submissions/me`）の読み込みが終わったら、表示中のHTMLを読み、提出ID・問題・結果（AC・WA・WJ・`3/10`など）を`submissions/<contest-id>.json`へ保存する。提出するとAtCoderはこのページへ移る。
- 色の元にするのは、アプリのブラウザで表示した提出一覧に載っている提出すべて。提出一覧にはどこで提出したかが書かれていないため、アプリの外で行った提出も、アプリで提出一覧を開いたときに反映する（利用者の判断、2026-11-06。以前は「アプリのブラウザで行った提出だけ」としていた）。
- 1問の色は、ACが1つでもあればAC、なければジャッジ中があればジャッジ中、どちらもなければAC以外。
- ジャッジ中の提出があるあいだは、そのWebViewが提出一覧を表示していれば、数秒ごとに表示中の内容を読み直す（ページが書き換えるため通信は増えない）。
- 読み取りの固定データには、利用者がログインした状態で保存したページ（ジャッジ中と判定後）を使う。ユーザー名とトークンは置き換えてから入れる。
- 提出一覧は1ページに20件までで、読むのは表示中のページだけ。21件より古い提出は、その一覧のページを開いたときに反映する。
- 利用者の手元の確認（2026-11-07）で、ジャッジ中に別の問題へ移る（提出一覧のWebViewを隠す）と、色がジャッジ中のまま変わらなかった（別のブラウザではACになっていた）。隠したWebViewの提出一覧は当てにできないため、U5bで取得する。

### U5b. ジャッジ中に提出一覧から離れた場合

- 判定が出る前に、提出一覧を表示していたWebViewを隠した・別のページへ移した場合だけ、自分の提出一覧を10秒ごとに、提出から最大10分まで取得する（[取得の方針](problem-library.md#atcoderからの読み取りの規約と頻度u0の調査)）。
- U5aの手元の確認で、隠したWebViewの提出一覧では色が更新されなかったため、隠した場合も取得する。
- 3秒ごとの読み直しのたびに、その提出一覧のWebViewが表示中で、まだ提出一覧を表示しているかを確かめる。どちらかでなければ、読み直しをやめて取得に切り替える。提出の時刻は、ジャッジ中の提出一覧を読み込んだ時刻とする（提出するとAtCoderは提出一覧へ移るため）。
- 取得は共用のWebViewのCookieで行い、1つのコンテストにつき同時に1つだけにする。ジャッジ中の提出がなくなるか10分たったらやめる。取得に失敗しても10分までは取り直す。

### U5c. 全サンプル一致時のクリップボードと設定

- 比較が有効なサンプルがすべて一致した状態で実行が終わったら、毎回、開いているファイルのコードをクリップボードへコピーし、実行ボタンの左に知らせる（利用者の判断、2026-11-07。ステータスバーの知らせは小さく、実行前から全部一致のときはコピーも知らせもしなかったため）。
- 左端のバーの一番下に歯車を置き、設定のダイアログでオン・オフを切り替える。最初はオン（利用者の判断、2026-11-06）。設定は枠の大きさと同じく画面の`localStorage`に置き、`settings.json`は作らない。
- ステータスバーの実行制限の説明に残っていた、C4より前のWindowsのメモリ上限の説明を直す。

### U6a. 参加登録の検知と、終了後の非表示

- 右端のブラウザでコンテストのトップ（`/contests/<id>`）の読み込みが終わるたびに、参加登録の状態と開始・終了の時刻を読む。参加登録していて終了から1日たっていなければ、アイコンを追加する（登録済みなら時刻を更新する）。参加予定のコンテストの一覧ページはないため、アプリの外で参加登録したコンテストは、アプリのブラウザでそのトップを開いたときに追加する。
- 参加登録の状態は、ログインした利用者の名前の横の「(Contestant)」で判断する。参加登録の前は「(Guest)」。「参加登録を取り消す」は開始前にしか出ないため使わない。時刻はページのスクリプトの`startTime`・`endTime`（タイムゾーン付き）を読む。
- `contests/<contest-id>.json`に、参加登録で追加したこと（`joined`）と開始・終了の時刻を任意項目として加え、問題一覧を0件でも許す（開始前は問題一覧を見られないため）。どれも任意項目の追加と件数の緩和で、既存の形式はそのまま同じ意味で読める（[保存形式を変えるときの方針](problem-library.md#保存形式を変えるときの方針)）。
- 問題一覧のないコンテストを選んだとき、開始前なら開始の時刻を案内し、開始後なら問題一覧を1回取得する。開始時に自動で取得して最初の問題を開くのはU6b。
- 起動時と1分ごとに、参加登録で追加したコンテストのうち終了から1日たったものを非表示にし、`joined`を外す。自動で非表示にしたものを利用者が表示に戻したら、もう自動では非表示にしない。
- 読み取りの固定データには、利用者がログインした状態で保存したABC483のトップ（参加登録の前と直後、どちらも開始前）を使う。

### U6b. 開始時に問題一覧を取得して最初の問題を開く

- 参加登録で追加したコンテストの開始時刻になったら（アプリの起動中だけ）、問題一覧を取得し（まだ見られなければ5秒ごとに最大1分まで取り直す）、最初の問題を開く。別の問題を編集中でも切り替える（利用者の判断、2026-11-06）。切り替えは今の問題を開く処理と同じで、保存してから開き、実行中なら開かずに案内する。
- 開始前にそのコンテストを選んで待っている場合も、開始時刻になったら同じく問題一覧を取得して最初の問題を開く（利用者の要望、2026-11-08）。
- 対象は、アプリの起動中に開始時刻を迎えたコンテストだけ。起動したときに既に始まっていたコンテストは、選んだときに問題一覧を取得する（U6a）。開始時刻は画面が1秒ごとに確かめ、時計はWindowsのものを使う。

### U6c. 開始1分前の通知

- 参加登録で追加したコンテストの開始1分前に、アプリ内の案内とタスクバーの点滅で知らせる（アプリの起動中だけ）。
- Windowsのトーストは使わない（利用者の判断、2026-11-08）。インストールしていないアプリのトーストは、アプリの識別子（AppUserModelID）をレジストリかスタートメニューのショートカットで登録しないと出ず、ポータブル版でレジストリに書くことを避けた。アプリを開いていないときの通知（タスクスケジューラーへの登録・常駐・カレンダーへの追加）も作らない。
- 案内は画面の一番上のバー（右端のブラウザはAtCoderのページを画面の上に重ねるため、その上には出せない）に「<コンテスト名>があと1分で始まります（開始 21:00）」と出し、閉じるボタンで閉じられる。開始時刻を過ぎたら自動で消す（開始時はU6bで最初の問題を開く）。開始1分前より後に起動・参加登録した場合も、開始前なら1回知らせる。タスクバーの点滅は、ウィンドウが前面に来るまで続く（Tauriの`requestUserAttention`）。

## Phase C：Rubyの実行とLSPをWSLのエージェントへ

### C0. 調査（資料と小さな試作）

- `wsl.exe`経由の標準入出力（1行ずつのJSON）の安定性、日本語、大量出力。
- WSLの起動時間（初回と2回目以降）と、エージェントの動作中はWSLが止まらないこと。
- Windows側から停止を依頼したとき、WSL内のプロセス群が確実に止まるか。
- コードは本文としてエージェントへ送り、実行時の作業フォルダーはWSL内の一時フォルダーにする（U2aで保存先のフォルダーで実行する仕様はなくなるため、`C:\…`と`/mnt/c/…`の読み替えは不要）。日本語を含むコード・入出力の受け渡しを確認する。
- Linux版Ruby 3.4.5を、YJIT付き・配置場所に依存しない形（`--enable-load-relative`など）でCIでビルドできるか。対象のディストリビューションは`wsl --install`の既定（Ubuntu）。
- メモリ上限（`setrlimit`かcgroupか）と、ネイティブスタックの上限（`RLIMIT_STACK`）の扱い。
- GitHubのWindows環境でWSL1が使えるか。使えなければ、Windows側は偽のエージェントで確かめ、本物のエージェントはLinuxのCIで確かめる。
- 結果：WSL1は使えたがWSL2は使えなかった。WindowsのCIではWSL1と本物のエージェントでやり取りと停止を確かめ、WSL2でしか確かめられない項目は利用者の手元で確かめる（[構成と検証方針](architecture.md#rubyの実行環境の調査c0)）。

### C1. 資料の書き換え

- mvp.md（M10・M12・M19など）、architecture.md、atcoder-runtime.md、README.mdを「WSL2が必須、RubyはWSL内」の構成に書き直す。WSLの準備手順と、Windows 10 Homeでも使えること（仮想化を有効にする必要がある）を書く。

### C2. エージェント化

- 画面テスト用ホスト（`ui-test-host`）の通信方式をもとに、本番用のエージェント（Linux向けのバイナリ`atcoder-ruby-agent`）と、エージェントを起動して要求を中継するクライアント（ライブラリの`AgentClient`）を作る。Runner・LSP管理は既存のUnix向けのコードを使う。
- 画面テスト用ホストは、Rubyの実行・停止・補完をクライアントから自分自身のエージェントの動作（別プロセス）へ送る。LinuxのCIでは、本物のエージェントのバイナリと、クライアントを通した画面テストで全テストを回す。
- Windowsのアプリはまだ同梱のRubyを直接使う（切り替えはC3a）。途中のmainでもWindowsのアプリが動くようにし、C2は利用者のWindowsでの確認なしにマージできる。

### C3a. アプリ専用のディストリビューションと中継

- C0の方式でRuby 3.4.5（YJIT付き）をUbuntu 22.04でビルドし、静的ライブラリとデバッグ情報を除いて、エージェント・採用gem・LSP用gemとともに、Ubuntu 22.04の最小構成のアプリ専用のディストリビューションに入れる（ソースのSHA-256を固定）。初回起動時と版が変わったときに`wsl --import`で登録し、インストール版はアンインストールで登録を解除する。
- Windowsのアプリは起動時にエージェントを1つ立ち上げ、実行・停止・補完を中継する。ネットワークのポートは開かない。Ruby LSPも同じRubyで動かす。
- WSLがない・起動できない場合の案内を出す。
- 開発・LinuxのCIのRubyも3.4.5にし（`config/ruby-wsl.json`）、Ruby LSPの固定（Rubyに含まれるgemの版）を3.4.5に合わせる。2つのRubyの版を保守しないため、WindowsのCIは単体テストをやめ、配布物の画面テストとインストール版の確認を、WSL1と本物のエージェントで行う。使われなくなるWindows版Rubyの準備・コード・測定の削除はC4で行う。
- WindowsのCIでは、WSL1で本物のエージェントとのやり取り（日本語・大量出力）と停止を、配布物の画面テストを通して確かめる。
- 実行がWSLへ切り替わるため、利用者のWSL2でのC0の確認結果を見てからマージする。

### C3b. C拡張のあるgemとLSPの解析対象

- 既存の5つのgemに加え、ネイティブgem（rbtree、sorted_set、immutable-ruby、bit_utils、fast_trie、numo-narray、rumaleなど）を入れる。どこまで入れるかを理由付きでatcoder-runtime.mdに書く。
- 競技用gemをRuby LSPの解析対象に加え、ac-library-rbなどのAPIも補完候補に出す。先に、現状で競技用gemが解析対象に入っていないことをテストで確認する。競技側の実行からLSP用gemが見えないという既存の分離は維持する。

### C3c. ディストリビューションの初回ダウンロード

- 配布物（ポータブル版・NSIS）からLinuxのイメージを外す。アプリには、ビルドしたイメージの版・URL・SHA-256を埋め込む。
- CIは、イメージを1つのGitHubのリリース（`wsl-images`）に、イメージのSHA-256を名前にした資産として置く。同じ資産は置き直さない。イメージはビルドごとにバイト列が変わるため、版（中身のハッシュ）ではなくSHA-256で区別する。PRのポータブル版を確かめられるよう、PRのCIでも置く。90日より古い資産は消す。リポジトリは公開されているため、アプリは認証なしで取得できる。
- 初回起動と版が変わったときに、進捗を表示しながら取得し、SHA-256を確かめてから登録する。取得したファイルは登録の後に消す。失敗したときは理由を表示して再試行でき、編集・保存は続けられる。
- 初回だけネットワークが要ることをMVP・READMEに書く。取得のテストはイメージを配るローカルのHTTPサーバーで行う。WindowsのCIは、同じ実行で置いたリリースから実際に取得する。

### C4. Windows版Rubyの関連を削除

- C3aで使われなくなったWindows版Rubyの準備（`prepare:ruby`・`update:ruby`・`config/ruby-windows.json`）、Job Object、測定のスクリプトとCIのジョブ、それらのテストを削除する。

### C5. 実行環境をAtCoderに近づける

- AtCoderと同じく`--jit`で実行する。メモリ上限・スタックの上限をLinuxの仕組みで設定する。メモリ上限は`RLIMIT_AS`を使わず（Rubyが仮想メモリを先に確保するため）、cgroupか使用中のメモリ（RSS）の監視で設定する。スタックは起動前の`RLIMIT_STACK`と`RUBY_THREAD_VM_STACK_SIZE`で広げる。どちらもC0の利用者の手元での確認結果をもとに決める。
- 決定（2026-11-04）：メモリ上限は、エージェントがRubyのプロセスグループの使用中のメモリ（RSS）を50ミリ秒ごとに調べ、問題のメモリ制限（不明なら1024 MiB）を超えたら止める。cgroupは通常のユーザーが書けず、`RLIMIT_AS`はRubyの仮想メモリの確保で使えないため。`/proc`はWSL1にもあり、WSL1でも上限が効く。WSL1では`--jit`を付けるとRubyの起動に毎回約8秒かかったため、`--jit`を付けず、そのことを画面に表示する。VMスタックとネイティブスタックは、どちらも問題のメモリ制限（不明なら1024 MiB）にする。
- 時間超過の注意表示の説明をJITありの前提に更新する。

## Phase D：残りの候補（使ってみて困った順）

### D1. 入力中に補完の候補を自動で開く

- VS Codeのように、識別子の文字と`.`・`&.`の入力で候補を自動で開く（利用者の判断、2026-11-04）。
- 自動で開いた候補は何も選ばず、Enterは改行のままにする。`end`と打ってEnterを押したときに、候補が選ばれて改行されないことを防ぐため。上下キーで選んだときだけEnterで挿入する。Ctrl+Space・「補完」で開いたときは今どおり先頭を選ぶ。
- 候補を表示している間のTabは、選んでいる候補（何も選んでいなければ先頭の候補）を挿入する。候補を表示していないときのTabは字下げのまま（利用者の判断、2026-11-05）。
- Ruby LSPは最初の補完（自動の表示を含む）で起動する。

### D2. 読み込みのコードの対応形式を広げる

- ABC460〜ABC479の全140問の問題ページを取得し（1秒に1回）、生成したコードがすべてのサンプル入力を読み切れるか（整数に変換する値が整数か、読み残しがないか）を実Rubyで調べた（2026-11-09）。読み切れたのは118問で、コードが入らなかったのが19問、誤ったコードが入ったのが2問、入力の形式がないインタラクティブの問題が1問だった。
- 入らなかった19問のうち14問は複数のテストケース（`T`と`case_1`〜`case_T`、各テストケースの形式は別の`pre`）。ほかは、先頭の値が行の長さの縦の並び（`K_i A_{i,1} … A_{i,K_i}`）、`\vdots`の代わりの`\dots`、`{\rm Query}_i`、2つずつ並べた縦の並び（`A_1 A_2`〜`A_{2N-1} A_{2N}`）が1問ずつ。誤った2問は、「`A`、`B`、`C` のいずれか」の変数を整数として読んでいた。
- 複数のテストケース、先頭の値が行の長さの縦の並び、`\dots`の縦の並び、`{\rm …}`、「いずれか」の文字列に対応する。テストケースの中の`X_1 Y_1 R_1 X_2 Y_2 R_2`・`P_x P_y Q_x Q_y`のような番号付きの値の行にも対応した。2つずつ並べた縦の並びは1問だけで、読み方の形も決めにくいため対応しない。インタラクティブの問題には入れない。
- 対応後、ABC460〜ABC479は140問中138問が読み切れた（残りは2つずつの縦の並びとインタラクティブ）。対応する形を決めるのに使っていないABC300〜ABC309の70問でも、mainの62問から66問に増え、読めなくなった問題はなかった。この確かめで見つかった`N_1 N_2 M`と、間に何もない`$…$`の並び（ABC305 C）にも対応した。残る3問は、`C[1][1]`のような角括弧の添字、問題ごとに行数を書いた行と値の行を交互に並べた形、3つの表を続けた形。
- 読み込みのコードの生成と`task.json`の`inputFormat`の詳細は[問題ライブラリ](problem-library.md#読み込みのコードの生成)にある。

### D3. るりまの全文検索

- 右端の列に、上からスライドする窓でるりまを表示し、URL欄・F1・右クリックから全文検索する（利用者の要望、2026-11-09）。仕様は[画面の仕様](ui.md#るりまの全文検索d3)にある。
- るりまサーチは全文検索をやめ、名前の検索だけになっていた（2026-11-09に確認）。全文検索はGoogleで、`<語> site:docs.ruby-lang.org/ja/latest/`の検索語で行い、最新版のページは同じ場所の3.4のページで開く（利用者の判断。るりまの各版は最新版を正規のページとしており、Googleには最新版のページだけが載っているため）。窓は列の幅の8割・高さの9割の、るりまの青で縁取った角の丸い枠にし、中にるりまのURL欄・全文検索の検索欄・ページを収める。窓が出ている間はAtCoderのページを撮った画像を暗くして後ろに見せる（利用者の要望、2026-11-10）。
- 右クリックの項目はTauriにないため、WebView2の`ContextMenuRequested`で加える。Windowsでしか動かず、WindowsのCIでもメニューは操作できないため、利用者の手元で確かめる。項目を選んだ後の処理（窓を開いて検索）は、画面テストでイベントを送って確かめる。

### D4. 入力から有向グラフ・木を表示する

- 選択中のサンプルの入力から、辺の列（`N M`と`u v`・`u v w`）または親の配列（`P_2 … P_N`）を読み、グラフ・木を描く。形は問題の入力形式から判定し、判定できない・違うときは手で指定できる。有向・無向の切り替え（初期は無向）、重みの表示、木は根（1番）を上にした階層、ほかは自動の配置。100頂点まで。拡大縮小と頂点のドラッグ。「Rubyを再確認」の右のボタンで、AtCoderのページと同じ位置に上からスライドする窓で表示する（利用者の判断、2026-11-09）。D3の後に進める。
