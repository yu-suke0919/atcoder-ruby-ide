# 問題ライブラリの準備

## 保存先の方針

問題集・問題文・サンプル・解答は、配布フォルダーと別のユーザーデータ領域へ保存する。
Rust で Tauri の `app.path().app_local_data_dir()` を解決する。Windows では通常 `%LOCALAPPDATA%\io.github.yu-suke0919.atcoder-ruby-ide` になる。インストール先やカレントディレクトリ、OS の一時キャッシュ領域には依存しない。

後続の問題取得機能で次の構成を使う。

```text
<app_local_data_dir>/
  library/
    collections/<collection-id>.json
    problems/<contest-id>/<task-id>/problem.json
    problems/<contest-id>/<task-id>/assets/
  workspaces/<contest-id>/<task-id>/
    solution.rb
    cases.json
```

library は取得した問題のデータ、workspaces は自分の編集内容を置く。問題の更新で解答や編集済みケースを書き換えない。
80 問程度は一覧 JSON と問題単位のファイルで扱う。1 問あたりのサンプル上限 100 件とは別の単位とする。
問題取得・HTML 抽出・画像や数式のオフライン表示・ユーザーデータへの実保存は後続の機能で実装する。この整理ではディレクトリを先に作成せず、既存のソース／ケース JSON の保存先と形式を維持する。

## 今回のリファクタリング

- `src/sample-cases.mjs` に DOM・Tauri・ファイル I/O へ依存しないケース管理を置く。生成、選択、追加・削除、保存対象、未保存判定、判定無効化、実行スナップショットを担当する。
- renderer は画面描画とイベント、実行・停止、ファイル操作を担当する。実行予約やプロセス制御は既存 Runner のままにする。
- ケースの置換は `SampleCases.replace(data, { saved })` に集約する。JSON 読み込みは `saved: true` で保存済み状態を更新する。取得データは既存の保存済み状態と比較し、入力が変われば未保存とする。
- 置換時は新しいケースをすべて用意してから反映し、選択を先頭へ戻す。stdout / stderr・比較・不一致詳細は引き継がない。
- 実行中のケースの参照は維持する。スナップショットは開始時の入力・期待出力・比較設定・リビジョンを固定し、編集による無効化で古い判定を復活させない。
- 取り込むデータの型とバイト数の検証は既存 Rust の責務とする。画面モデルは 1〜100 件と最後のケースを削除しない条件を維持する。
- 新しいフレームワーク・依存・汎用ストアは追加しない。保存形式の変更やデータ移行は行わない。

## 受入条件

資料 → 失敗する単体テスト → 最小実装 → 不要コード・資料矛盾の確認の順で進める。

- 入力以外の結果・選択・リビジョンで未保存扱いにならず、保存前後と編集の取り消しを正しく判定する。
- JSON と取得データの置換で保存済み状態を区別し、置換失敗時は内容と選択を保持する。
- 実行中の参照とスナップショット、選択ケース／全ケースの判定無効化を DOM なしの Node テストで確認する。
- 既存 GUI 全 38 件を Linux・Windows で通し、NSIS スモークと配布前照合も維持する。
