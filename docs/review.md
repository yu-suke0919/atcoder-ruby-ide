# レビューで維持する修正

Electron 版の [PR #1](https://github.com/yu-suke0919/atcoder-ruby-ide/pull/1) と
期待出力比較の [PR #2](https://github.com/yu-suke0919/atcoder-ruby-ide/pull/2) で確認した挙動を、Tauri 版でも維持する。
実装の共存や互換レイヤーは作らず、Rust の共通テストと実際の Windows 配布アプリで確認する。
全体レビューで見つかり、直した挙動（R1〜R9）も、テストとコードのコメントからこの資料を参照する。削除した機能へのレビューの対応（PR #26〜#32）は[検証記録](verification.md)とgitの履歴にある。

| ID | 保持する修正 | 現在の検証 |
| --- | --- | --- |
| R01 | CRLF を含む解答ファイルを開いた直後に変更扱いにしない。エディターに代入した後の値を保存済みバッファにする | 作業領域の CRLF ファイルを開く GUI テスト |
| R02 | 一時ファイル削除が失敗しても実行中状態を解除する | Rust の RAII による予約解除、POSIX の権限変更テスト |
| R03 | 最小ウィンドウ・大きな行高でも入力と結果を 1 行以上表示し、実行ボタンに重ねない | Windows GUI のレイアウトテスト |
| R04 | 出力上限で切れた UTF-8 末尾を文字化けさせない。先に手動停止した場合も上限到達を独立して扱う | Rust の末尾デコード・停止と上限の重複テスト、GUI は最終出力に同期 |
| R06 | 保存は比較結果・実行中の比較を保持する | 自動保存・`Ctrl+S`・実行中の保存の GUI テスト |
| R07 | 画面再読み込みで保存中・保存失敗の変更を確認し、初期化時に実行をリセットする。初期化前の保存を別の問題の作業領域へ書かない | 共通 GUI の保存失敗時の再読み込み確認、実行中の初期化 |
| R08 | 期待出力・比較設定の編集で、未編集の標準入力や期待出力の改行を変えない | 共通 GUI の CRLF / CR ケースと実 Ruby のバイト列・JSON 保存 |

保存では比較の状態に触れないことで R06 を実現する。
ハッシュや保存イベントの世代番号など、同じ内容を表す別の状態は増やさない。
実行中に入力を編集した場合の判定無効化は、ケースごとの比較リビジョンで扱う。

## PR #60の時点の全体レビューへの対応（2026-11-05）

`1e010e8`（PR #60）のコードと照合した。R1〜R5はいずれも妥当。R5はPR #60で直し、R1〜R4と資料の不整合はこのPRで直した。

| 指摘 | 判断と対応 |
| --- | --- |
| R1 | 妥当。Rustが問題を開いた後に画面がその応答を捨てると、Rustの開いた文書と画面の表示がずれ、表示中の解答が別の問題へ保存されていた。開いた応答は、その間に別のコンテスト・問題を選んでいても表示する（後から選んだ問題はその後に開く）。さらに、`DocumentStore`は開くたびに版を進めて結果に載せ、保存は画面が送る版が今開いている版と一致するときだけ行う。応答を止めて別のコンテストを選ぶ画面テストで、表示中の問題のファイルにだけ保存されることを確かめる。 |
| R2 | 妥当。タブの切替・追加・コピー・開いているファイルの削除とホームへの切替で、前のファイルの保存を編集と操作を止める前に始めていた。保存から切替までを`fileAction`の中で行い、保存中は編集できないようにした。保存の応答を止めた間にエディタが編集できないことを画面テストで確かめる。 |
| R3 | 妥当。省略記号だけの行のように変数のない行で、入力形式の解析が`unwrap()`でpanicした。その行は当てはまらない行として扱い、読み込みのコードを入れない。 |
| R4 | 妥当。保存に失敗した後に保存済みの内容へ戻しても、失敗の表示と終了・切替時の確認が残った。保存の必要がなくなったら失敗を解除する。 |
| R5 | 妥当（PR #60で対応）。候補が開いた直後と、入力に合わせて候補を取り直している間のTabが、何もしないか字下げになっていた。候補が確定できるようになるのを待って挿入する。 |

資料の不整合も直した。READMEは、Rubyを初回起動時にダウンロードするLinuxに入れること、WSL1でもメモリ上限が効きJITは使わないこと、手元の`npm run prepare:wsl`で作ったイメージはリリースにないためWindowsのアプリが取得できないことを書いた。構成と検証方針は、イメージを取得・照合してから古い登録を解除する順序と、取得に失敗したら古い版が残ることを書いた。補完の自動表示の説明はPR #60で直した。

## PR #64の時点の全体レビューへの対応（2026-11-08）

`5983fcd`（PR #64）のコードと照合し、U6a・U6bを加えた`9481b4d`でも同じく再現した。4件とも妥当で、資料の残り2件と合わせてこのPRで直した。

| 指摘 | 判断と対応 |
| --- | --- |
| R6 | 妥当。提出結果の「読む→まとめる→保存」を直列にしていなかったため、2つのスレッドが同時に提出を加えると、後から保存した側がもう一方の提出を消した（10回中10回）。提出一覧の再読み込みで読み直しが二重に走ったときや、2つのWebViewで提出一覧を開いたときに起きる。プロセスで1つの排他の中で読み込みから保存までを行う。2スレッドから同時に加えて両方が残ることをRustのテストで確かめる。参加登録（U6a）の保存は、コンテストの登録と同じ排他の中で行っており、同じ問題はない。 |
| R7 | 妥当。コンテストを選んだときの色の取得（`submission_states`）の応答が、その間に届いた`submissions`イベントの色を古い色で上書きした。コンテストごとにイベントを受けた回数を数え、取得の間にイベントを受けていたら、その取得の応答を使わない。取得の応答を止めた間に提出一覧を読ませる画面テストで、ACの色が残ることを確かめる。 |
| R8 | 妥当。制約で小数と述べた変数も整数として`to_i`で読み、ABC169 Cの`1.10`が`1`になった。小数（「小数」「実数」）と述べた変数は文字列として読み、変換は利用者に任せる（利用者の判断、2026-11-08。`to_f`では誤差が問題になる問題で値が変わるため）。ABC169 Cの制約で、`a, b = gets.split; [a.to_i, b]`の形になることを確かめる。 |
| R9 | 妥当。保存に失敗したサンプル（誤差許容0など）を残したまま、ファイルの切り替えで「破棄して続ける」を選ぶと、タブは変わるがサンプルの変更と失敗の表示が残り、戻るときにも同じ確認が出た。ファイルの切り替えでも、破棄を選んだらサンプルと誤差許容を最後に保存した内容へ戻す。画面テストで、破棄後に誤差許容が保存済みの値に戻り、確認が再び出ないことを確かめる。 |

資料の残りも直した。構成と検証方針の「WSL1ではメモリ上限が効かないことの表示は…C5で加える」を、C5の実装（WSL1でも使用中のメモリを監視し、JITを使わないことを表示する）に合わせた。ホームの保存は`home_save_cases`ではなく、`samples_save`に`home`を渡す。
