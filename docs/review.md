## 追加レビューへの対応

- R04: 手動停止・タイムアウトの要求後に出力上限へ到達すると、停止理由が保持されるため、従来の理由による判定ではデコーダをフラッシュしてしまう。バイト数で上限を判定し、停止理由と独立して出力を打ち切る。両方の停止理由と stdout / stderr の不完全な UTF-8 末尾を再現テストで確認する。
- R05: Windows の停止直後に残るハンドルによる一時的な削除失敗には、`fs.rm` の標準オプション `maxRetries: 3, retryDelay: 50` を使う。独自のリトライ処理は追加しない。既存の停止・一時ファイル削除のテストと、リトライ対象外の `EACCES` を使う R02 のテストを維持する。

資料を先に更新し、R04 のテスト 2 件が修正前に `ready\n�` を返して失敗することを確認した。
実プロセスへの停止要求後、終了イベントの前に残りのパイプ出力を渡し、OS のタイミングに依存せず再現している。
修正後は両方のテストが成功し、最初の停止理由・出力イベント・stdout / stderr の内容も維持される。
本体の変更は上限判定 2 か所と削除オプションだけとし、状態変数や抽象化を増やしていない。
Linux の共通・画面テストと R02 も成功した。Windows の一時的なハンドル保持は故意に再現しておらず、
R05 は Node.js 標準のリトライを利用する。Windows の停止・削除を含む通常の動作は下記 CI で検証する。

## 期待出力比較の追加レビュー

- R06: `updateEditor()` が無条件に比較表示をリセットするため、同一ファイルへ上書き保存しただけで一致・不一致が未比較になる。
  指摘は妥当。同じパス・コード・入力であれば判定の前提は変わらず、表示を保持すべきである。
  比較リセットを実際の編集・ファイル切替に移し、保存では既存のパスと保存先が変わった場合のみリセットする。
  汎用的な状態管理やキャッシュ、パス正規化の仕組みは追加していない。
  画面テストで上書き保存時と実行中の保存時の失敗を再現し、修正後の成功を確認した。
  一致・不一致の保持に加え、初回保存・別名保存でのリセット、キャンセル・失敗時の保持も確認した。
