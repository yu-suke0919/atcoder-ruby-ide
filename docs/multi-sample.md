# 複数サンプル

## ケースと実行

- ケースは 1〜100 件。入力・期待出力・比較の有効状態・実行結果を個別に保持する。追加時は空入力・空期待出力・比較有効とする。
- 「実行」と Ctrl+Enter は選択ケースだけ。「全件実行」は表示順に既存 Runner を呼ぶ。同時実行は 1 件。
- 全件実行の開始時にコード・全ケースの入力・期待出力を固定する。実行中も編集とケース切替は可能だが、追加・削除・ソースの新規作成・読み込み・保存先変更はできない。同じソースへの上書き保存は可能。
- 各ケースの時間制限は 5 秒、入力・出力上限と比較ルールは既存どおり。エラー・時間制限・出力上限は記録して次へ進む。手動停止と終了操作は現在の Ruby と残りの実行を中止する。
- 問題の時間制限が分かる場合は、実行開始時の制限値を超えたケースに「制限超過の可能性」を表示する。比較結果とは独立し、編集による無効化や制限値の再取得は[問題の制限値](problem-library.md#問題の制限値)に従う。結果と同様に保存対象には含めない。
- ケース選択で入力と結果を切り替え、実行済み数・一致・不一致・エラー件数を一覧表示する。未実行を一致に数えない。
- コード・作業ディレクトリが変われば全ケースの判定を無効にする。ケースの編集はそのケースだけ無効にする。実行中に変更しても古い実行の判定を復活させない。
- ケースはソースの読み込み・新規作成では維持する。最終 1 件は削除できない。最小画面 900×650 と大きな行高でも編集・入力・結果・ボタンを利用できる。

## JSON の保存・読み込み

- 「ケース保存」で UTF-8 JSON の `{ "cases": [{ "stdin": "", "expectedOutput": "", "compare": true }] }` を保存する。通常は毎回保存先を選び、AtCoder の問題選択中はその問題の作業領域へ保存する。結果・選択位置・ソースは含めない。
- 「ケース読込」はケースだけを置き換える。ソースとその作業ディレクトリは変更せず、先頭ケースを選んで実行結果を消去する。
- 問題選択中にケースJSONを取り込んでも、作業領域の保存済み内容を未保存判定の基準として保持する。取り込んだ内容が保存済み内容と異なる場合だけ未保存として扱い、同じ内容なら未保存にしない。
- 入力・期待出力・比較設定・追加・削除はケースの未保存変更として扱う。実行とケース選択は変更扱いにしない。読込と終了では未保存ケースを破棄する前に確認する。ソースの新規作成・読込ではケースを維持する。
- 選択キャンセル・不正 JSON・I/O 失敗では現在のケース・判定・未保存状態を維持する。保存は同じディレクトリの一時ファイルから置き換え、失敗時に既存 JSON を壊さない。
- ケースは 1〜100 件、各入力・期待出力は UTF-8 で 1 MiB 以下、JSON 全体は 16 MiB 以下。型・必須項目・範囲を Rust で検証する。読み込みは上限付きとし、UTF-8 BOM を許容する。
- 保存・読込は実行中に行えない。ファイル操作中はケースの編集も抑止する。

資料 → 失敗する UI テスト → 最小実装 → 不要コード・資料矛盾の確認の順に進める。

## ケースJSONの形式を変えるとき

[開発ルール](../AGENTS.md)と[保存形式変更の判断基準](problem-library.md#保存形式を変えるときの方針)を、手動保存したケースJSONと問題別のworkspaces内のcases.jsonの両方に適用する。旧形式の自動変換・移行や、互換維持だけを目的とした未知項目の無視・必須項目の既定値補完は追加しない。互換のためだけに必須項目を省略可能にすることも行わない。

判断基準にある条件を満たし、未設定を新しいデータでも有効な状態とする任意項目の追加は、この禁止事項に当たらない。既存ケースを従来と同じ意味で読めるなら、作り直しは求めない。

- SampleFile・SampleCaseの変更は、利用者のケースだけでなく、同じSampleCaseを含む問題JSONと問題集原本にも影響しうる。影響範囲と、追加項目の未設定の意味を資料に記す。
- 任意項目の追加では、その項目を含まない既存のケースJSON（手動保存・作業領域の両方）が、定めた未設定の意味で、従来と同じ判定・表示で読めることを固定データの回帰テストで確認する。未知項目や不正な型・範囲を拒否するテストも維持する。
- 編集済みの入力・期待出力・比較設定はAtCoderから再取得しても戻らない。旧形式が読めないことを理由に削除したり、取得したサンプル・空ケースで黙って初期化したりしない。

### 作り直しが必要な変更

- ケースJSONが読めなくなる、または保存内容の意味が変わる変更では、元JSONをそのまま退避・保持し、利用者が明示的に現行形式のケースを作り直して再開できる手段を同じPRに含める。複数の作業領域が影響する場合も、ファイルを1件ずつ探して削除するだけの復旧手順にはしない。旧ケースは自動変換せず、必要な編集内容は保持した元JSONを参照して手動で再入力する。この作り直しが必要なことを操作前に案内する。
- 値の意味が変わる旧データを現行形式として黙って受理しないための表現変更は、問題ライブラリの判断基準に従う。
- 退避先の既存データや解答ソースを上書きしない。元JSONを保持できなければ作り直しを開始せず、キャンセル・退避・保存の失敗時は元ファイルと現在の編集内容・保存先を保持する。
- 作り直しが必要な変更PRでは、旧JSONの入力・期待出力・比較設定が元のバイト列のまま保持されること、解答の保持、作り直し後の保存・読込・実行、キャンセルと失敗時の保持を検証する。未知項目や不正な型・範囲を拒否するテストも維持し、Linux・Windowsの全テストと配布検証をPRのCIで確認する。

## 受入条件

- ケース別の結果、エラー・時間制限後の継続、開始時のコードと入力、手動停止後の再実行を確認する。入力検証エラーの詳細もケース別に保持する。
- JSON の往復保存、比較無効時の期待出力、空期待出力、BOM、日本語・空白のパス、不正な型・サイズ・件数、キャンセル・失敗時の保持、終了時の未保存確認を検証する。
- 900×650 と大きな行高のレイアウトを確認する。Windows では同じ GUI ケースを WebView2 と実ダイアログで実行し、NSIS スモークと配布前照合を最終 CI で行う。
- stdio ホストの EOF・巻き戻しでは Ruby の停止と待機に加えて、実行イベント送信スレッドを join する。Runner が idle になった直後も最終イベントの送信が残るため、JSON 行を途中で切らずに終了することを回帰テストで確認する。
