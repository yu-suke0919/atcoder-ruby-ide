# 構成と検証方針

## 最小構成

- Tauri v2 の Rust コマンドが作業領域のファイル I/O、AtCoderからの取得、同梱 Ruby の実行を担当する。
- HTML / CSS / JavaScript は既存の画面を使う。bridge.mjs が Tauri の invoke / Channel と画面をつなぐ。
- コード編集は同梱CodeMirror 6で行い、editor.mjsが文書内容・読取専用状態・カーソル・変更通知を画面へ渡す。Ruby用モードと必要な拡張をesbuildで1つのES Moduleへまとめ、依存のライセンスを同梱する。CodeMirrorが生成する表示用CSSをCSPで許可し、スクリプトは同梱ファイルに限定する。
- ruby-completion.mjsが同梱の基本候補・定型コードとCodeMirrorの文書内単語収集を組み合わせる。この基本候補はRubyプロセスや外部サービスを使わず同期生成する。表示・選択・挿入はCodeMirrorに任せ、手動で開く。
- lsp-completion.mjsが手動補完時にShopify Ruby LSPへ接続し、候補をCodeMirrorへ渡す。要求を直列化し、無効になった文書・カーソルの応答を捨てる。既存のruby-completion.mjsを基本候補・定型コード・LSPが候補を返せない場合の補完として共有し、候補は表示名で重複を除く。専用gem・固定bundle・文書同期・UTF-8／UTF-16位置変換・終了処理は[Ruby LSP](ruby-lsp.md)を参照する。
- ruby-methods.mjsがString・Array・Hashのメソッドと引数・説明を保持する。ruby-receivers.mjsは既存Rubyモードの字句情報を使い、直前のリテラルと、単純な直接代入に続くローカル変数の型を有界に識別する。同じ行の単純代入・自己再代入・連鎖代入の右辺や括弧内でも代入前の型を使う。コメント・文字列中の代入を除外し、未知の文やスコープ境界では推定を解除する。改行をまたぐ未完の文やdef・undef・aliasの文脈も型を確定しない。確定できなければ一般候補へ戻す。候補詳細はCodeMirrorのinfoを使い、最小画面でも領域内に収める。
- Rust の実行・ファイル操作・期待出力比較は GUI に依存しないモジュールとし、Linux でも実プロセスでテストする。
- 入力検証とファイルパスの管理は Rust で行う。ファイルは問題の作業領域（ユーザーデータ内の固定パス）だけを読み書きし、利用者が選ぶパスやネイティブのファイルダイアログは使わない。
- Electron と本番 Node.js ランタイム、旧バックエンドの二重実装は残さない。Node.js は開発・配布準備・テストに使う。

画面の CSP と Tauri capabilities で API を絞り、出力はテキストとして表示する。AtCoderのページを表示するWebViewからアプリの機能を呼べないようにする方法は[画面の作り直しの調査](#画面の作り直しの調査u0)に従う。

## 実行・出力・停止

Ruby は shell を介さず起動する。コードを一時 UTF-8 ファイルに書き、標準入力を渡して EOF を送る。
bootstrap で標準入出力を UTF-8 binary mode、stdout / stderr を同期出力にする。
Runnerの子RubyはVMスタックを32 MiBに固定する。LSPと共有するCommand生成関数では設定しない。再帰の受入範囲とネイティブスタックに残る差は[実行環境の資料](atcoder-runtime.md)を参照する。
作業ディレクトリは常に実行ごとの一時ディレクトリとする。

同時実行の予約をコマンド受付時に確保し、プロセス開始前の停止も保持する。
実行予約時にRustで打ち切りを確定する。Tauri Channelでは最初にstartedでexecutionLimitMsを送り、その後バイト列の出力、最後に確定値を含む完了またはエラーを送る。打ち切りの式とケース別の保持は[実行の打ち切り時間](atcoder-runtime.md#実行の打ち切り時間)に従う。画面は TextDecoder でチャンク間の UTF-8 を維持する。
Rust は上限内の stdout / stderr を保持し、完了時の表示・比較は確定値を使う。
stdout／stderrの受信・バイト数の集計・停止判定は、逐次通知のコールバックと別のスレッドで行う。通知が遅れても受信とプロセスの制限を進める。通知キューに入れるデータも受信上限内に限定し、各ストリームの通知順を保つ。完了・エラーを返す前にキューの通知を終え、途中の通知が完了イベントを追い越さないようにする。
逐次出力の追加はテキストで行い、スクロール位置の更新は画面フレームごとにまとめる。大量出力時のチャンクごとの再レイアウトを避ける。
停止理由は最初の要求を保持する。出力上限に達したときは通知キューへ渡す前に停止理由を確定し、プロセス群を停止する。その通知を受けてから手動停止しても、確定済みの出力上限を理由に保つ。先に手動停止・時間制限が確定していた場合はその理由を保つ。出力上限は理由とは独立した受信バイト数で判定し、不完全な UTF-8 末尾を追加しない。Rubyと受信処理が終わった後の通知待ちを時間制限の対象にしない。
Windowsはkill-on-closeのJob Object、POSIXはプロセスグループを使う。Windowsは停止状態で起動し、Jobへ割り当ててからメインスレッドを再開する。親Rubyが先に終了しても子プロセスを管理する。停止・時間制限・出力上限・検知したメモリ上限ではプロセス群を終了する。RunnerのJob全体はコミット1 GiBに制限し、確保拒否通知は実行ループで確認する。LSPにはメモリ上限を設定しない。[上限の意味と通知の制約](atcoder-runtime.md#windowsの実行メモリ上限)を参照する。終了後の削除に失敗しても実行予約を解除する。
Windows の一時的な共有違反・ロック・削除競合は短い待機で最大 3 回再試行する。

異常終了時は確定したstderrから実行ソースの絶対パスに一致する最初の有効な行番号を抽出し、RunResult.errorLineで返す。ケースモデルは比較結果と同じリビジョンで位置を失効させる。editor.mjsは専用のStateFieldでエラー行を強調し、コード変更時はそのトランザクション内で強調を解除する。行番号の抽出とジャンプの仕様は[実行エラー](run-errors.md)を参照する。

Windows のデスクトップアプリは開発時・配布版とも resource directory の ruby/bin/ruby.exe を直接使い、外部の RUBY_PATH や PATH に依存しない。
Linux のデスクトップアプリと、両OSの共通テスト・ブラウザー用テストホストは RUBY_PATH または PATH の Ruby を使う。Windows CI の共通テストでは RUBY_PATH に準備済みの vendor/ruby/bin/ruby.exe を指定する。
起動時のRuby確認は問題に関係なく5秒を上限とする。確認失敗時は「Ruby を再確認」から再試行でき、確認中は重複確認と実行を抑止する。編集・保存は確認の成否に依存しない。
Ruby は SHA-256 を固定した RubyInstaller から実行用ファイルを用意する。bin/・lib/ とライセンスを保持し、share/・include/ は除外する。share 内の COPYING・LEGAL は licenses/ruby/ に退避する。ネイティブ gem のビルドと同梱オフラインマニュアルは対象外。
Rubyはconfig/ruby-windows.jsonへ検証済みの3.4系パッチを固定し、Linux CIも同じパッチを使う。update:rubyだけが公式Ruby・RubyInstallerの一覧から最新3.4.xを選択し、アーカイブとgemの準備後に固定情報を更新する。通常ビルドやアプリ利用時には最新版を探索しない。AtCoderの公開バージョンと追加gemはconfig/atcoder-runtime.jsonに残す。RubyGemsのアーカイブをSHA-256検証し、C拡張のない採用gemと依存gemをローカルインストールする。WindowsはステージングしたRubyの標準gemディレクトリへ追加してから配置し、取得元またはgem構成が変われば作り直す。Linuxはprepare:gemsで選択したRubyへ同じ構成を用意する。[AtCoderとの比較](atcoder-runtime.md)を参照する。
RunnerはCommandのenv_removeでRUBYOPT・RUBYLIB・BUNDLE_GEMFILE・GEM_HOME・GEM_PATHを子プロセスの環境から除外してからRubyを起動する。bootstrapもGem.use_paths(Gem.default_dir)で、そのRubyの標準gemディレクトリだけを探索先にし、ユーザー用gemを含めない。prepare:gemsの既定の追加先もGem.default_dirとする。

## 文書と比較状態

Rust は問題の作業領域の解答ファイルと UTF-8 の読み書きを管理する。解答ファイルは UTF-8 のファイル全体（BOM を含む）を 1 MiB 以下とし、開く時点と保存時に検証する。解答ファイルと`cases.json`は共通の上限付き読み込み・同じディレクトリの一時ファイルからのアトミック置換を使う。失敗時は既存のファイルを保ち、読み込み時に BOM を除く。
画面は編集内容と保存済みの内容を比べ、変更を作業領域へ自動で保存する。保存の状態（保存中・保存済み・失敗）を表示し、失敗時は編集内容を残して再試行できる。保存に失敗したまま問題を切り替える・ウィンドウを閉じる場合だけ、アプリ内のダイアログで確認する。
ウィンドウを閉じる際は保存中の書き込みを終え、実行中なら停止と完了を待ってから閉じる。画面再読み込みは beforeunload で保存中・保存失敗の変更と実行中を保護する。
画面起動時は実行停止・終了待機を行い、完了するまで編集・実行を抑止する。初期化に失敗した場合はエラーを表示し、操作を有効にしない。
保存では比較結果や実行中の比較を消さない。

期待出力は null が比較なし、空文字列が空出力との比較を表す。Rust は型と最大 1 MiB を検証する。
正常終了時だけ stdout と期待出力の CRLF / CR を LF に揃え、末尾の LF を最大 1 つ除いて比較する。
Runner は最初の不一致を 1 回だけ計算し、一致判定と詳細を RunResult に載せて送る。画面は結果を再比較せず、ケースの判定と同じリビジョンで詳細も保持・無効化する。
不一致の表示はスクロール可能なダイアログに置き、Unicode スカラー値で差の前後 40 文字を表示する。本文は text node と mark で構築する。
コード・入力・期待出力・比較設定・許容誤差・実行するファイルが変われば未比較に戻し、古い判定を表示しない。
高さ 720px 以下は装飾的な見出しを省き、入力・期待出力・出力を最低 1 行表示する。

## ケース管理と検証

`cases.json`の型・件数・入力サイズ検証と I/O は Rust の samples モジュールを共有する。保存は一時ファイルからの置換とし、解答ファイルには触れない。
ケースモデルは保存対象の入力・期待出力・比較設定・許容誤差を直近保存時と比較して保存が必要かを判定し、画面は自動保存の状態を表示する。実行結果やサンプルの選択は保存対象に含めない。

複数サンプルの入力・結果・選択・保存済み状態と begin / finish / fail / cancel による判定遷移は DOM 非依存の sample-cases.mjs が保持する。renderer は描画とイベント、既存の run コマンドの逐次呼び出しを担当する。Rust の実行制御は変更しない。
開始時にコード・サンプルを固定し、実行中はファイル・問題の切替を抑止する。編集による判定の無効化はケースごとのリビジョンで行う。ケースの編集では、操作したフィールドだけをモデルへ反映する。textarea の改行正規化で未編集の入力・期待出力を変更しない。
問題を開く処理だけがサンプルを作業領域の内容へ置き換え、保存済み状態として扱う。
問題ライブラリは Rust の library モジュールが、コンテスト・問題集の登録と問題一覧、問題ページからの読み取り、作業領域を管理する。保存先は app_local_data_dir とし、読み取った内容と利用者のデータを分ける。[問題の取得・保存・切替の仕様](problem-library.md)を参照する。AtCoderへの取得はRustのMutexで直列化し、ブラウザのCookieを使う。取得で現在の問題・編集内容は切り替えない。
画面は4列（アイコン・問題一覧・エディタとサンプル・AtCoderのページ）で、AtCoderのページは選択中のコンテスト・問題集の問題ごとに子のWebViewとして表示する。エディタ・サンプル・問題一覧は領域内でスクロールし、実行ボタンはコード欄の下に固定する。ダイアログを開いている間だけ既存のショートカット抑止を適用する。

Linux の画面テストは headless Chromium とローカル HTTP 配信を使う。テスト専用 Rust ホストが本番の Runner・作業領域・RunEvent を共有し、実 Ruby・一時ファイル I/O・停止・比較を実行する。
テスト側で Tauri 通信とウィンドウ操作を差し替える。通常の GUI テストでは、登録・問題一覧・問題ページの読み取りの成功／失敗も、必要に応じてブリッジの応答と保存データをテスト側で用意する。HTTP・HTML解析・保存の処理は Rust テストで検証する。JavaScript にRubyの実行制御を再実装せず、本番フロントエンドにもテスト分岐を追加しない。
Windows と Linux は同じ画面の受入ケースを使い、Windows では WebView2 と、AtCoderのページを表示する子のWebViewの分離を確認する。

1. Rust 共通テストで実 Ruby・停止・制限・UTF-8・作業領域のファイル操作・比較を確認する。
2. Node で Ruby の取得整合性、削減対象・ライセンス保持、展開済みランタイムの再利用を確認する。
3. Linux でも画面の編集・実行・停止・比較・自動保存・保存失敗時の確認・レイアウトを検証する。Linuxのテスト専用ホストだけATCODER_IDE_UI_TIMEOUT_MSで既定上限を短縮でき、ブラウザーE2Eは不明時に4秒を使う。本番とWindowsネイティブE2Eの既定は5秒。制限既知は両OSとも本番の5〜30秒の式を使う。全件は数十秒を目安とし、件数と時間の実測は verification.md に記録する。
4. Windows ポータブル配布物の全 GUI テストは 1 周。NSIS 後はexe と主要ファイルの存在を確認し、アプリ経由のサンプル実行・問題を開く操作・同梱 Ruby のパスに絞る。
5. Ruby が PATH にない条件は両 Windows 配布形態で維持する。Ruby の元ファイルのハッシュ一覧は 1 回生成し、GUI テスト後の配布対象を 1 回照合する。インストール先の全件走査や ZIP 作成時の再計算は行わない。

検査ポートは専用の環境変数を指定した場合だけ有効。通常起動では開かない。Linux のテスト専用ホストは開発依存だけを使い、配布物に含めない。
初回の Chromium・OS 依存導入と Rust ホストのコンパイル時間を、画面テスト単体の時間と分けて記録する。

E2E は各テスト前に共通リセットで問題を開いていない状態・空の結果へ戻し、必要な問題と入力を各テストで準備する。Windows の終了確認は OS のウィンドウ終了要求を使い、フロントエンドの close 権限には依存しない。

Windows E2E の CDP 接続は検査ポートのブラウザー引数で有効にし、devtools feature と開発者ツール UI は配布ビルドで無効にする。

## コマンドとRuby起動の共通処理

本番とUIテストホストはRuby検出、問題の作業領域を開く処理、自動保存をライブラリで共有する。Ruby検出は成功時にversionのみを返し、失敗時はエラーを返す。Ruby実行とLSPは同じCommand生成関数で環境変数とプロセス設定を揃える。RUBYOPT・RUBYLIB・GEM_HOME・GEM_PATH・RUBYGEMS_GEMDEPS・BUNDLE_*・BUNDLER_ORIG_*を大文字小文字によらず除去する。準備スクリプトも同じ除去規則を使う。

Unixでは停止後250 msで出力パイプが閉じない場合も実行予約を解放する。読み取りはノンブロッキングで停止可能にし、プロセスグループを離れた子孫がパイプを保持しても次の実行を妨げない。ただしsetsidなどでグループを離れた子孫自体は終了できず、実行後も残りうる。WindowsではJobの終了によって子孫とパイプが閉じる前提で、ブロッキングの読み取りスレッドを待つ。

問題一覧と問題ページの取得・検証は、ブラウザのCookieを受け取る同じHTTP処理にまとめる。問題を開く処理は作業領域を受け取るコールバックで共有し、ロック方式は呼び出し側が決める。

## 右端のブラウザと問題の読み取り

[画面の作り直しの調査](#画面の作り直しの調査u0)の結論を、次のように実装する。

- 右端の列はHTMLの`#browser-host`で場所だけを確保し、画面がその位置と大きさをRustへ送る。Rustはメインウィンドウに子のWebViewを置き、見せるものだけを`#browser-host`の位置に重ねる。ウィンドウの大きさが変わったら画面が送り直す。
- 子のWebViewは「ホーム」1つと、選択中のコンテスト・問題集の問題ごとに1つ。ホームは問題を選んでいないときに表示し、選択中のコンテストのトップ（なければ`https://atcoder.jp/`）を開く。ログインや、問題一覧の取得に使うCookieの読み取りにも使う。問題のWebViewは問題を初めて選んだときに作り、別のコンテスト・問題集を選ぶと閉じる。
- `on_navigation`で`https://atcoder.jp`以外への移動を止める。AtCoderのページが別ウィンドウで開こうとするリンク（`target="_blank"`など）は、AtCoder内なら同じWebViewで開き、それ以外は開かない。
- 問題のWebViewで、その問題のページの読み込みが終わり、`task.json`がない・読めない場合は、Rustが`eval_with_callback`でHTMLを受け取り、サンプルと制限値を読み取って`task.json`へ保存する。画面へは`task-page`イベントで知らせる。読み取れなかった場合（問題文がない。ログインしていない・参加登録していない・ページが存在しない）は理由を付ける。
- 問題を開く操作は、`task.json`が読めればすぐ作業領域を開く。なければ問題のWebViewを開いて読み取りを待ち、`task-page`を受けて作業領域を開く。理由が付いていればブラウザでのログイン・参加登録を案内する。開いたことのある問題を選び直したときに`task.json`がなければ、そのWebViewで問題のページを読み込み直してから読み取る（ログインする前のページを読まないため）。
- 操作欄（U2c）：移動の許可は、許可するオリジンの一覧（今は`https://atcoder.jp`だけ）で判定する。`on_navigation`・新しいウィンドウ・URL欄からの移動のすべてで同じ判定を使い、後で設定から一覧へ追加できるようにする。戻る・進むは表示中のWebViewでRustが`history.back()`・`history.forward()`を実行し、更新は`Webview::reload`を使う。URL欄は、表示中のWebViewの読み込み開始（`on_page_load`）と表示の切り替えのたびにRustが画面へURLを送って更新する。どれもアプリの画面から操作し、AtCoderのページからアプリの機能を呼べない分離は変えない。
- 子のWebViewを作る・動かすコマンドは非同期にする。同期コマンドはメインスレッドで動き、WindowsではWebView2の作成などがデッドロックする（PR #42のWindows CIで、問題を開くと画面が応答しなくなった）。
- 画面テストのため、`ATCODER_IDE_TEST_ORIGIN`を指定した場合だけ、子のWebViewが開くURLの`https://atcoder.jp`をその値（ローカルのHTTPサーバー）に置き換え、移動の許可もその値にする。通常起動では使わない。LinuxのブラウザーE2Eは子のWebViewを持たないため、テスト用ホストが読み取りの処理を直接呼び、同じイベントを画面へ送る。

## 画面の作り直しの調査（U0）

[画面の仕様](ui.md)の右端のブラウザについて、2026-10-31にTauri 2.12.5（wry 0.57.1）のソースとWindows CIの試作で確かめた結論。U2以降の実装はこの節に従う。試作は`spike/u0-embedded-browser`ブランチにあり、マージしない（[検証記録](verification.md#画面の作り直しの調査u0)）。

### 埋め込み

- Tauriの`unstable`機能の`Window::add_child`で、メインウィンドウにAtCoder用のWebViewを子として追加する（試作はラベル`atcoder`の1つ）。設定ファイルで作るメインウィンドウにもそのまま追加でき、`on_page_load`で読み込みの開始・完了とURLを受け取れる。
- 右端のブラウザは、選択中のコンテスト・問題集の問題ごとに子のWebViewを1つ持ち、選んだ問題のものだけを表示する。表示中のURLとスクロール位置はWebView自体が保つため、アプリでは記憶しない。WebViewは問題を初めて選んだときに作り、別のコンテスト・問題集を選ぶと前のWebViewを閉じる。
- `unstable`のAPIはTauriのマイナー更新で変わり得る。Cargo.lockで版を固定し、Tauriを更新するときはこの節の確認をやり直す。
- 画面テストでは、子のWebViewにもメインウィンドウと同じ`additional_browser_args`（リモートデバッグのポートを含む）を渡す。同じWebView2の環境を共有するため、引数が違うと作成に失敗する。ログイン状態は同じプロファイル（`WEBVIEW2_USER_DATA_FOLDER`）に置かれる。

### 分離

AtCoderのページからアプリの機能を呼べないよう、次の3つを組み合わせる。

1. capabilityは`webviews: ["main"]`で画面のWebViewだけに与え、`windows`は書かない。`windows`で指定すると、同じウィンドウの子のWebViewにも同じ権限が付く。`remote`も書かない。Tauriはリモートのオリジン（`https://atcoder.jp`）からの呼び出しを、`remote`を指定した権限がない限り拒否する。
2. アプリのコマンドを`build.rs`の`tauri_build::AppManifest::commands`で宣言し、`allow-<コマンド>`を画面のWebViewのcapabilityにだけ付ける。宣言がないと、ローカルのオリジン（`tauri.localhost`）からのアプリのコマンドは権限を確かめずに実行される。試作では、AtCoderのページに`http://tauri.localhost/`のiframeを差し込むとアプリのページが読み込まれ、宣言があることで`ruby_info`などが拒否された。
3. AtCoder用のWebViewは`on_navigation`で`https://atcoder.jp`以外への移動を止める。ページ全体の移動は止まるが、iframeの読み込みは止まらないため、2を省略しない。外部サイトへのリンクは開かない。新しいウィンドウで開くAtCoderのリンクは同じページで開く（[右端のブラウザと問題の読み取り](#右端のブラウザと問題の読み取り)）。

試作のWindows CIでは、AtCoderのページから`ruby_info`・試作のコマンド・通知・ウィンドウのタイトル変更がすべて「not allowed by ACL」で拒否され、IPCのURLへ直接送った要求も500で拒否された。画面のWebViewからは同じコマンドを実行できた。

### ページからの読み取り

| 方法 | 結論 |
| --- | --- |
| A. RustがAtCoder用WebViewのCookieを受け取り、同じURLを取得し直す | ブラウザが表示しないページ（問題一覧など）にだけ使う |
| B. AtCoderのページにスクリプトを入れ、ページからアプリへ内容を送る | 不採用 |
| C. Rustが`Webview::eval_with_callback`でページの内容を読む | 表示したページに使う |

- Cは、ブラウザが読み込んだページのHTML（`document.documentElement.outerHTML`）をRustが受け取り、既存の`scraper`で解析する。読み取りを始めるのは常にRustで、AtCoderのページからアプリを呼ぶ手段はない。ページの取得はブラウザの1回だけで、アプリは取得し直さない。
- Aは`Webview::cookies_for_url`でHttpOnlyを含むCookie（`REVEL_SESSION`など）を受け取り、既存の`reqwest`と`scraper`で取得・解析する。Windowsでは同期コマンドから呼ぶとデッドロックするため、非同期コマンドから別スレッドで呼ぶ。
- Bは読んだ内容をアプリへ渡すためにAtCoderのページへIPCを許す必要があり、分離と矛盾する。
- 読み取りのきっかけは`on_page_load`の完了で受け取るURLにする。問題ページは、その問題の`task.json`がない・読めない場合だけCで読む。参加登録はURLが変わらず、同じコンテストのトップに「参加登録しました。」が出るだけのため、コンテストのトップの読み込みのたびにCで参加登録の状態を読む。提出すると自分の提出一覧（`/contests/<id>/submissions/me`）へ移動する。頻度と範囲は[AtCoderからの読み取りの規約と頻度](problem-library.md#atcoderからの読み取りの規約と頻度u0の調査)に従う。
- ログイン状態はページの`userScreenName = "…"`で判断する（空ならログインしていない）。
- 自分の提出一覧のジャッジ中の表示（WJ、`26/103`のような進み具合）は、AtCoderのページがその場で書き換え、ページを読み込み直さない。結果が出ても`on_page_load`は起きないため、ジャッジ中の提出があるあいだ、その問題のWebViewが提出一覧を表示していれば、Cで数秒ごとにページの内容を読む（通信は増えない）。WebViewを別のページへ移した場合だけ、Aで提出一覧を取得し直す。利用者の確認では、提出から結果まで約13秒だった。
- 提出の画面にはCloudflareの確認（Turnstile）があり、利用者がブラウザで通す。アプリは提出しないため影響しない。
- 試作では、Cで問題ページのHTML（約59 KB、サンプル3件）を読め、読み取りでページの読み込みは起きなかった。AtCoderのページから試作の読み取りコマンドを呼ぶと権限で拒否された。隠した子のWebViewでも1秒ごとのタイマーは15秒で15回動き、`document.visibilityState`は`visible`のままだった。Aでは、ログインしていないCookieで問題ページから200・サンプル3件、自分の提出一覧から302（ログイン画面へ）を得た。ログインは試作のexeを開き直しても残った。AtCoderには参加予定のコンテストの一覧ページがないため、参加登録はアプリのブラウザで行ったものだけを検知する。

### 通知とクリップボード

- クリップボードは、画面のWebViewの`navigator.clipboard.writeText`で書ける。試作で書いた文字列をPowerShellの`Get-Clipboard`で読めた。プラグインは追加しない。
- トースト通知は`tauri-plugin-notification`で呼び出せ、権限も許可済みになったが、インストールしていない試作のexeでは利用者の画面にトーストが出なかった。Windowsはスタートメニューのショートカットなどでアプリの識別子（AppUserModelID）が登録されていないアプリのトーストを表示しないためと考えられる。U6でインストール版で表示されるかを確かめ、出なければ通知の方法を決め直す。ZIP版ではトーストを出さない前提とする。
